# Languages: English and Gujarati

The app shows all of its own text in English or Gujarati. The person chooses in Settings
(Phone language, English, ગુજરાતી). Text typed by people (customer, item and package names,
notes) is never translated.

Words: [GUJARATI_GLOSSARY.md](GUJARATI_GLOSSARY.md). Follow it; change a word there first.

## Where things are

| What | Where |
|---|---|
| `t()` and the language | `src/i18n/index.ts`, `src/i18n/language.ts` |
| English text, by area | `src/i18n/locales/en/<area>.ts` |
| Gujarati text, by area | `src/i18n/locales/gu/<area>.ts` |
| Calendar words, units, counted nouns | `src/i18n/locales/common.ts` |
| Words of the date picker (react-native-paper-dates) | `src/i18n/calendar.ts`, keys `components.calendar.*` |
| Stable names for documents and modes | `src/i18n/entities.ts` (`DocumentEntity`, `AppEntity`, `EntityMode`) |
| The name of a stored role | `roleLabel()` in `src/utils/roleLabel.ts` |
| English / ગુજરાતી choice before sign-in | `src/components/LanguageSwitch.tsx` |
| Numbers, money, weight, dates | `src/utils/formatters.ts` (already follow the language) |
| The saved choice | `language` in `src/store/slices/themeSlice.ts`; `src/i18n/useAppLanguage.ts` |

Areas: `common` (words used everywhere: Save, Cancel, Search…), `auth`, `nav` (tab and screen
titles), `filters`, `lists` (the list screens and their cards), `grn`, `dispatch`, `invoice`, `orders`, `customers`, `items`, `pricing`,
`reports`, `settings`, `users`, `sensors`, `errors`, `validation`, `components` (shared
components that belong to no one area).

## Rules

1. **No English text in code that a person can see or hear.** That includes
   `accessibilityLabel`, `accessibilityHint`, placeholders, alert titles and buttons,
   snackbars, validation and error messages. Use `t('area.group.name')`.
   Not translated: log and console messages, test files, `app/style-guide.tsx`, the terms and
   privacy pages, text that comes from the backend or was typed by a person.
2. **Call `t` while rendering or inside a function, never at module level.** A constant
   built when the file is loaded keeps the language the app started in. Turn such constants
   into functions (`const stepLabels = () => [t('grn.steps.details'), …]`) or store keys and
   call `t` where they are drawn.
3. **Whole sentences with placeholders.** `t('grn.list.noMatch', { search })` with
   `'No GRNs match "{{search}}"'`. Never join translated pieces with `+` or a template string:
   Gujarati word order differs (the verb comes last; "from … to" follows its values).
4. **Counts.** A text that depends on a number is a pair:
   `showItems: { one: 'Show {{count}} item', other: 'Show {{count}} items' }`, called with
   `{ count }`. In Gujarati the noun does not change after a number, so both forms are
   usually the same text. For "N things" alone, `formatCount(n, 'item')` already works in both
   languages for the nouns listed in `locales/common.ts`; add a noun there if it is missing.
5. **Numbers and identifiers.** A `number` parameter is formatted for the language (Indian
   grouping; ૦-૯ in Gujarati). Pass amounts, weights and dates through the formatters first
   (`formatCurrency`, `formatWeight`, `formatDate`) and give `t` the resulting string.
   Identifiers (GRN, dispatch and invoice numbers, vehicle, GST, PAN, phone numbers, login
   codes) are passed as strings and are shown exactly as stored: do not format them.
   Never write a digit in Gujarati text by hand in Latin form: use ૦-૯ or a placeholder.
6. **Typed input.** Run `normalizeDigits()` on anything a person typed before parsing it as
   a number or matching it, so ૧૨ and 12 mean the same.
7. **Keys.** `area.group.name`, in camelCase, named for what the text is for
   (`grn.list.emptyTitle`), not for its wording. One text per meaning: reuse `common.save`
   rather than adding a second "Save". Do not reuse a key for a different meaning just
   because the English is the same.
8. **Both languages in the same change.** The Gujarati table is typed from the English one,
   so a missing or extra key does not compile. `src/i18n/__tests__/translate.test.ts` checks
   placeholders, plurals and script.
9. **Data values are not labels.** Do not show or capitalise a stored value such as `admin`
   or `in_stock`; map it to a key (`users.role.admin`).
10. **Layout.** Gujarati text is often longer and taller. Do not add fixed heights to text
    containers; let chips, buttons and rows grow, and keep `numberOfLines` where a row must
    stay one line. Do not rely on capital letters for emphasis: Gujarati has none.

## Shared components that speak about a document

A shared component must not build a sentence around a noun the caller passes
("Delete " + name + "?"): the Gujarati sentence has another order and the verb agrees with
the noun. Such a component takes a **stable name**, not a word, and picks a whole-sentence
key with it:

| Component | Props | Keys |
|---|---|---|
| `GenericStepIndicatorHeader` (and the GRN, dispatch and invoice step indicators) | `entity: 'grn' \| 'dispatch' \| 'invoice' \| 'customer'`, `mode: 'create' \| 'edit'` | `components.steps.cancelFor.<entity>.<mode>`, `components.steps.discardFor.<entity>` |
| `ActionsSection` | `entity: 'grn' \| 'dispatch' \| 'invoice'` | `components.actions.<entity>.*` |
| `PrintRangeDialog` | `entity: 'grn' \| 'dispatch' \| 'invoice'` | `components.printRange.<entity>.*` |
| `DocumentSuccessDialog` | `entity: 'grn' \| 'dispatch' \| 'invoice'`, `isEditMode` | `components.documentSuccess.<entity>.*` |
| `ItemsSummaryBottomSheet` | `entity: 'item'` (the default) | `items.summary.item.*` |

- Pass `entity` (and `mode`) from every screen. Never decide anything by comparing text that
  is shown (`entityName === 'Edit'`): it stops working in the other language.
- `entityName` on the step header is only the label next to the close button; it is not
  placed into a sentence when `entity` is given.
- The older word props (`entityType`, `label`, `entityName`, `documentType`) still work and
  give the English sentences they always gave. Do not use them in new code.
- A new kind of document needs its keys in both languages and a new member of the type in
  `src/i18n/entities.ts`; the type checker then points at every place that needs text.

A stored role is shown with `roleLabel(role)`; never capitalise `admin` or `staff` yourself.

Wizard step names have one source per wizard, a function called while rendering:
`grnSteps()` (`src/features/grn/utils/grnStepLabels.ts`), `dispatchSteps()`
(`src/components/DispatchStepIndicator.tsx`), `invoiceSteps()`
(`src/components/InvoiceStepIndicator.tsx`), `customerSteps()`
(`src/features/customer/customerStepLabels.ts`). `src/constants/*Steps.ts` hold only the step
numbers and counts.

## The `tr` alias

Many components already use `t` for the theme tokens (`const t = useTokens()`). In those
files import the translation function under another name:
`import { t as tr } from '@/i18n'` (a few files use `translate`). The guard test follows
the import, so any alias is checked.

## The language switch and screen state

Changing the language rebuilds the navigation tree (`key={language}` on `NavigationStack`
in `app/_layout.tsx`); that is what makes every screen change at once. A rebuilt screen
loses its local state. The Settings screen is where the language normally changes, so only
the sign-in screen needs care: it keeps the half-typed mobile number in
`src/utils/signInDraft.ts` (memory only, per facility, cleared after sign-in and when the
screen is left). A new screen that shows `LanguageSwitch` next to a field must keep that
field's value the same way, or subscribe with `useAppLanguage()` outside the keyed tree as
`OperatorServerSelection` does.

## The date picker

`DatePickerModal` (react-native-paper-dates) gets `locale={getLanguage()}`; never a fixed
`"en"`. English uses the library's own words; Gujarati is registered in `app/_layout.tsx`
from `components.calendar.*`. Month and weekday names come from `Intl.DateTimeFormat` with
that locale, and the day numbers and the year are drawn by the library in 0-9.

## Tests

Tests run in English, so assertions on English text keep working. To test Gujarati, call
`setLanguage('gu')` from `@/i18n` and reset it in `afterEach`.

Guard tests (`src/i18n/__tests__/guards.test.ts`) fail the suite when:

- `t` (under any alias) is called while a file is loaded: outside every function, method,
  accessor or instance member initialiser (rule 2);
- `scripts/i18n-report.mjs` finds visible English in code;
- a file calls `toLocaleDateString`, `toLocaleTimeString` or `toLocaleString` instead of the
  formatters.

`src/i18n/__tests__/consistency.gu.test.ts` fails when the same English text has two
different Gujarati texts in different areas. If the meanings really differ, add the English
text and the reason to `DIFFERENT_ON_PURPOSE` in that test; otherwise use one wording
(glossary and `common` first).

## Finding what is left

`node scripts/i18n-report.mjs [path…]` lists visible English text still written in code and
exits 1 when it finds any. English that is meant to stay (route names, sample addresses, the
GCSA wordmark, text that is only logged) is in the `ALLOW` list at the top of the script,
each entry with its reason; `--allowed` prints what the list skipped. Add to the list only
what no person reads in the app.

The report sees JSX text and the usual props. It does not see everything: also check
`showAlert(...)` arguments, messages of thrown errors that reach a screen, `|| 'fallback'`
values that are rendered, and numbers or dates shown without the formatters
(`toFixed`, `toLocaleDateString`).
